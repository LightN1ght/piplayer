# PiPlayer: архитектура

Актуальная версия и протоколы проверок: [CURRENT_STATE](CURRENT_STATE.md), [VALIDATION](VALIDATION.md). Аппаратная приёмка базового образа не переносится автоматически на обновлённый raw.

## Поток данных

```text
Компьютер: prepare-video.sh → MP4 H.264/yuv420p + AAC
    │ SFTP :22, сначала .part, затем rename в .ready.mp4
    ▼
/data/incoming → playerd/ffprobe → /data/media/current.mp4
                         │            │
                         │      FFmpeg -re -stream_loop -1 -c copy
                         ▼            ▼
              /run/player/status.json + /run/player/hls/<generation>/
                         │            │
                         └── nginx :8080 ── браузер: локальный hls.js / native HLS fallback
```

`player-publish` (POSIX shell + awk) читает приватные плейлисты и атомарно публикует `/run/player/stream.m3u8` для внешних программ. Общие media sequence, discontinuity и discontinuity sequence сохраняют фиксированный URL при смене поколения. После наполнения окно примерно 20–26 секунд, TARGETDURATION 6 секунд, вышедшие из окна сегменты удерживаются минимум 36 секунд. Состояние в RAM переживает рестарт publisher, но сбрасывается при reboot. Браузер остаётся на приватном generation URL. См. [HLS](HLS.md).

FFmpeg работает в одном экземпляре на активное видео. Нажатие кнопки в браузере не создаёт отдельный серверный поток. Клиенты могут иметь разную задержку из-за буферизации.

## Хранение и лимиты

Raw-образ состоит из отступа 1 MiB, FAT32 boot 64 MiB и ext4 384 MiB. Root и `/data` находятся в одном ext4-разделе; для пользовательского видео доступен его остаток после системы. При загрузке замены старый и новый файлы временно занимают место одновременно. Автоматического расширения раздела на всю карту в текущих исходниках нет.

Программный предел raw — 480 000 000 байт. Проверяются MBR, границы двух разделов, сигнатуры FAT32/ext4, disk signature и соответствие root PARTUUID в настоящем `cmdline.txt` внутри FAT32. Размер `.xz` и виртуальная ёмкость QEMU overlay не являются размером образа для записи на карту.

Активный ролик, SSH host key и настройки сохраняются на карте. HLS и рабочие логи размещаются в RAM, `/run/player` ограничен 96 MiB. FFmpeg создаёт сегменты примерно по 2 секунды и приватный плейлист на 5 сегментов; удалением старых файлов управляет publisher с удержанием опубликованных URI; длительность зависит от ключевых кадров исходника. Рекомендуемый битрейт и GOP обеспечиваются `prepare-video.sh`. Большой GOP/битрейт может исчерпать RAM; произвольный пользовательский MP4 не получает гарантии ресурсов только по факту успешного ffprobe.

## Протокол публикации видео

1. `*.part` игнорируются медиасервисом. Только переименование в `*.ready.mp4` означает окончание передачи.
2. ffprobe проверяет видеопоток H.264/yuv420p, наличие пакетов и AAC либо отсутствие аудио. Это проверка формата, а не полное доказательство безошибочного декодирования любого файла.
3. Поддержанный файл перемещается в `media/current.mp4`; неподдержанный получает `.rejected`, прежний поток продолжается.
4. Изменение активного файла запускает новый FFmpeg и новое `generation`. Старые HLS-сегменты удерживаются publisher для внешних клиентов; браузер переподключается по новому пути без конфликта кэша.
5. Поток циклический (`-stream_loop -1`), упаковка без транскодирования (`-c copy`). Смена видео и восстановление могут давать короткую буферизацию; бесшовный монтаж между разными файлами не гарантируется.

`status.json` публикуется через временный файл и rename. Контракт: `state` (`waiting`, `buffering`, `playing`, `error`), `generation`, `audio`, `error` (`unsupported_media`, `upload_failed`, `stream_failed`, `stream_stalled`, `missing_dependency`, `needs_preparation`, `buffer_busy` либо пусто). UI опрашивает его каждые 2 секунды. Watchdog отслеживает изменение плейлиста: отсутствие продвижения 60 секунд по умолчанию переводит сервис в `error/stream_stalled` и запускает восстановление. Перед TERM отправляется CONT, чтобы завершить также остановленный SIGSTOP процесс. При падении FFmpeg поток перезапускается с задержкой; BusyBox перезапускает сам `playerd`. Отсутствие `stat`, FFmpeg или ffprobe публикует `error/missing_dependency`. Для `stat -c` используется BusyBox fragment с STAT и FEATURE_STAT_FORMAT; обе опции и `/bin/stat` подтверждены в финальной сборке.

## Сеть и браузер

AP создаёт локальную сеть без объявления маршрута в Интернет и DNS. Ethernet использует DHCP; портов с разными продуктовыми режимами нет. nginx слушает `0.0.0.0:8080` и `[::]:8080`; это настройка привязки, а не гарантия назначения IPv6 или доступности через любой маршрутизатор.

При наличии MSE страница сначала использует локальный hls.js 1.6.13, затем native HLS как fallback. Кнопка запуска позволяет повторить play после отказа браузера. Чёрный фон и `object-fit: contain` сохраняют пропорции. Звук включается пользовательской кнопкой; эта же кнопка запрашивает fullscreen. Проверка `muted=false` не заменяет прослушивание, а запрос fullscreen не гарантирует его доступности в конкретном браузере.

## Сборка и граница QEMU

Buildroot не поддерживает пробелы в рабочих путях, поэтому проект копируется в `$PIPLAYER_WORK/project`. Рабочий путь по умолчанию — `${XDG_CACHE_HOME:-$HOME/.cache}/piplayer-build`. Архивы сохраняются в `.build/downloads`. Полная сборка и повторный `--configure` в `${XDG_CACHE_HOME:-$HOME/.cache}/piplayer-build` завершены; новая HLS/Ethernet-сборка также завершена и прошла чистые ARM VM проверки; подробные результаты приведены в VALIDATION. Изменения во время сборки нужно повторно синхронизировать запуском build.sh, поскольку staged-копия сама не обновляется.

Диск имеет signature `0x504c4159`, root ищется как `PARTUUID=504c4159-02`, независимо от имени блочного устройства. По умолчанию `run-qemu.sh` запускает ARM `virt`, Cortex-A72, virtio-net и virtio-blk. Используются **тот же Pi kernel Image и тот же raw**, встроенные VirtIO-драйверы; отдельной гостевой системы нет. Сетевые пробросы доступны только на localhost: `2222 → 22`, `8080 → 8080`.

`--raspi4` выбирает модель `raspi4b` с USB-сетью и SD. Только для неё создаётся частная копия Pi DT с USB, UART aliases и отключённым дочерним Bluetooth; аппаратный DTB не меняется. Эта модель полезна для проверки загрузки, но её измеренная HTTP-скорость 0,864–0,889 Мбит/с ниже битрейта demo около 1,1 Мбит/с. Возникающая буферизация не характеризует скорость физической Pi. ARM virt показал 103–130 Мбит/с; пользователь подтвердил плавное видео со звуком в Helium.

Для каждой модели используются `.build/qemu-$machine.qcow2` и `.build/qemu-$machine-base.sha256`, где machine — `virt` или `raspi4b`. Overlay имеет виртуальную ёмкость 512 MiB и не предназначен для записи на карту. Скрипт проверяет структуру raw и его SHA256 относительно overlay. Перед сменой raw остановить соответствующую VM; `scripts/run-qemu.sh --reset` (или с `--raspi4`) удаляет её тестовые данные и отказывается работать при активном QMP. Не менять backing raw работающей VM.

Чистая VM базового raw `8f4d68e8…` без ручных дополнений прошла smoke с reboot, SFTP, продвижением HLS, ненулевым AAC и восстановлением FFmpeg; журнал `.build/smoke-final.log`. Отдельная проверка того же raw на модели raspi4b также дала SMOKE PASS, включая повторный холодный запуск с ожиданием SSH (`.build/smoke-coldboot.log`). Ранние диагностические кандидаты с добавленным вручную stat не являются основанием для статуса финальной сборки.

Обе модели используют прямую загрузку kernel и сами по себе не подтверждают родной firmware boot, Wi-Fi AP и аппаратную производительность. Отдельные испытания на реальной Pi4B Rev1.2 уже подтвердили firmware boot с USB, AP и просмотр с телефона, Ethernet/SSH/SFTP, reboot, автономный холодный старт и прогон901с. Непроверенные сценарии перечислены в [VALIDATION.md](VALIDATION.md); аппаратный чек-лист — [HARDWARE_TEST.md](HARDWARE_TEST.md). Оперативное состояние сначала читать в [CURRENT_STATE.md](CURRENT_STATE.md).

## Приватные данные

`.local/` хранит генерируемые секреты; `dist/credentials.json` и `dist/admin_ed25519` входят в приватную поставку, но не в Git и не в публичный архив исходников. В образ попадают публичные ключи и необходимые настройки доступа. Не помещать содержимое секретов в логи, документацию, скриншоты и отчёты проверки.

## Дополнительное представление по адресам

Root `player-network` каждые 2 секунды строит `/run/player-network/presentation.map` по адресам из `STILL_INTERFACES`, проверяет nginx и выполняет graceful reload. `INTERFACE_MODES=0` сохраняет видео везде; при `1` выбранные destination IPv4/IPv6 получают статичный web root. Заголовок `X-PiPlayer-Mode` позволяет frontend автоматически переключиться. SSH/SFTP не ограничиваются; это не ingress/firewall-изоляция. В статичном режиме `/hls/…` и `/stream.m3u8` дают 404. JPEG публикуется `.part` → `/data/still/image.jpg`, иначе используется bundled SVG. См. [ETHERNET](ETHERNET.md).

S40network запускает DHCP для NIC, найденных при boot: USB-адаптер подключают до питания. Поздний кабель уже существующего NIC поддерживается; USB hotplug отдельно не реализован/не проверен. Для двух NIC QEMU virt используется `--dual-network` и отдельный `qemu-virt-dual.qcow2`; номера eth не соответствуют гарантированно порядку netdev.

Новый вход проверяется по реальным пакетам: GOP ≤4 секунд через границу цикла, суммарный видео/аудиобитрейт ≤6 Мбит/с по секундным корзинам и среднему. При менее 40 MiB свободного места tmpfs новая публикация ждёт (`buffer_busy`). Publisher — дочерний процесс playerd с heartbeat/watchdog; дополнительных Python-библиотек в target нет.
