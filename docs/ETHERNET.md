# Режимы представления по адресам интерфейсов

Дополнительный режим позволяет показывать статичную картинку по адресам выбранных интерфейсов, сохраняя видео по остальным адресам PiPlayer. HTTP-порт в обоих случаях один: **8080**. Режим выключен по умолчанию и не меняет обычный сценарий видео на всех адресах.

**Статус на 6 ноября 2026:** актуальный образ собран из исходников с optional Ethernet и фиксированным HLS URL. Чистая двухсетевая ARM VM прошла `.build/smoke-interface-hls-final.log`: STILL SMOKE PASS с reboot, IPv4/IPv6, JPEG и HLS, включая `/stream.m3u8` 404 на статичном адресе и 200 на видеоадресе. Базовый smoke с reboot и прямой HLS также прошли. Хостовые 17 тестов PASS за 54,225 секунды.

Текущий `dist/piplayer-rpi4.img`: **470 810 624 байта**, SHA256 `a111a19f1347ed81cf75625a5b08aae4ef1b4f7d01e9cb9833362152505e00cb`. XZ: 29 121 940 байт, SHA256 `62dbe6c74f7167cbbb10bcedf006894b81a93d6a6825cc2b5fbd1a3377a94001`.

`INTERFACE_MODES=0` остаётся значением по умолчанию. На физической Pi пока работает прежний базовый образ без этих функций; новый raw и два физических NIC на плате не проверены. Ранее в браузере на Ethernet-версии подтверждены автоматические переходы видео → картинка → видео и продолжение видео на втором адресе. Историю промежуточных образов и точные границы см. в [VALIDATION](VALIDATION.md); оперативный статус — [CURRENT_STATE](CURRENT_STATE.md), внешний поток — [HLS](HLS.md).

## Как выбирается режим

Решение принимается по **локальному адресу назначения HTTP-соединения**. Демон получает назначенные IPv4- и IPv6-адреса интерфейсов из списка статичного режима; адреса в состояниях `tentative` и `dadfailed` не включаются до готовности. Подключение к одному из этих адресов получает страницу с картинкой; остальные адреса сохраняют видеоплеер.

IP клиента, HTTP-заголовок `Host` и порт клиента режим не выбирают. Например, запрос к адресу выбранного Ethernet-интерфейса остаётся статичным, даже если маршрутизация привела этот запрос через другую сеть. Это управление представлением, **не строгая firewall-изоляция**. SSH/SFTP этой настройкой не ограничиваются.

Raspberry Pi 4 B имеет один встроенный Ethernet-порт. Его имя обычно `eth0`, но проверяйте фактические имена: USB-адаптер может называться `eth1`, `enx…` или иначе. Привязка по MAC не зашита; список имён задаётся конфигурацией. Без второго адаптера физический сценарий с двумя Ethernet-портами не проверен. USB Ethernet-адаптер подключайте **до подачи питания** на Pi: `S40network` запускает DHCP для интерфейсов, найденных при загрузке. Позднее подключение кабеля к уже существующему NIC поддерживается работающим udhcpc; позднее появление самого USB NIC отдельно не поддержано и не проверено.

## Настройка на устройстве

Войдите на Pi по административному SSH. Не выполняйте init-скрипты образа на компьютере сборки. Посмотрите реальные интерфейсы и их адреса:

```sh
ip link
ip addr
```

Настройки находятся в `/etc/player/player.conf`. Это **shell-конфигурация, читаемая root**: редактировать её должен администратор. Сохраняйте корректные кавычки и существующие параметры AP; не добавляйте в файл посторонние команды.

Для стандартного поведения оставьте:

```sh
INTERFACE_MODES=0
STILL_INTERFACES='eth0'
```

При `INTERFACE_MODES=0` список не влияет на страницу: видео доступно по всем адресам, как в базовой версии.

Чтобы адреса `eth0` показывали картинку:

```sh
INTERFACE_MODES=1
STILL_INTERFACES='eth0'
```

Для нескольких выбранных интерфейсов используйте имена через пробел, например:

```sh
INTERFACE_MODES=1
STILL_INTERFACES='eth0 eth1'
```

В последнем примере картинка включена на адресах обоих указанных интерфейсов. Все остальные интерфейсы, включая `wlan0`, сохраняют видео. В примере только с `eth0` интерфейс `eth1`, если он существует, также сохраняет видео.

Root-демон `player-network` проверяет конфигурацию и адреса каждые 2 секунды и применяет изменения через graceful reload nginx. Ручной перезапуск AP для этих параметров не нужен. Возможен небольшой переходный период: опрос, reload и обновление страницы не происходят одновременно. Graceful reload не обещает мгновенного закрытия всех прежних соединений.

При возврате к `INTERFACE_MODES=0` открытые страницы автоматически возвращаются к видео после обновления карты и проверки режима frontend. Для определения режима используется заголовок `X-PiPlayer-Mode: still` либо `X-PiPlayer-Mode: video`; статичная страница также отслеживает изменение карты. После перехода к видео браузер может потребовать действие пользователя для звука.

## Картинка

Встроенная заглушка находится в `/usr/share/player/still/placeholder.svg`. Статичная страница запрашивает `/still-image.jpg`: nginx сначала ищет `/data/still/image.jpg`, затем отдаёт `/placeholder.svg` из статичного web root. Если загрузка картинки завершается ошибкой, `still.js` также переключает `img` на `/placeholder.svg`. Пользовательская картинка — **JPEG**, загружаемый от `player` по SFTP. Каталог `/data/still` создаёт root с владельцем `player`.

1. Передайте JPEG как `/data/still/image.part`.
2. Дождитесь завершения передачи.
3. Переименуйте файл в `/data/still/image.jpg`.
4. Обновите открытую статичную страницу, чтобы увидеть новую картинку.

Не переименовывайте PNG в `.jpg`: сначала преобразуйте его на компьютере, например с FFmpeg:

```bash
ffmpeg -n -i original.png -frames:v 1 image.jpg
```

После этого загрузите полученный JPEG описанным способом. JPEG не проходит отдельную серверную проверку содержимого: корректность формата обеспечивает загрузивший файл пользователь. Собственный SVG или PNG как пользовательская картинка не входят в этот контракт; SVG используется только для встроенной заглушки.

В статичном режиме страница показывает `img` на чёрном фоне и не подключается к HLS. Запросы `/hls/…` и фиксированный HLS URL `/stream.m3u8` по статичному адресу получают HTTP 404. Сам общий видеопоток продолжает обслуживать видеоадреса; загрузка и администрирование по SSH/SFTP доступны в обоих режимах.

## Примеры проверок

Ниже — сценарии повторной проверки новой сборки. Подтверждённые программные результаты перечислены выше; для другой среды или изменённого образа фиксируйте отдельный результат. Сначала убедитесь, что проверяете образ с функцией, а не прежний базовый образ. Используйте прямые IP-адреса устройства, чтобы не спутать DNS и выбор режима.

### 1. Картинка и видео на разных адресах

С `INTERFACE_MODES=1` и `STILL_INTERFACES='eth0'` откройте адрес `eth0` и адрес другого интерфейса, например AP `192.168.50.1`, с портом 8080. На первом ожидается картинка, на втором — прежнее видео со звуком после нажатия кнопки. В заголовках ответа сравните `X-PiPlayer-Mode`.

Для проверки с компьютера замените значения переменных фактическими адресами. `192.0.2.10` ниже — пример, не адрес Pi:

```bash
STILL_IP=192.0.2.10
VIDEO_IP=192.168.50.1
curl -sSI "http://$STILL_IP:8080/"
curl -sSI "http://$VIDEO_IP:8080/"
```

Возьмите **существующий путь плейлиста** из сетевых запросов видеостраницы (`/hls/<generation>/index.m3u8`). Один и тот же путь должен отдаваться по видеоадресу и возвращать 404 по статичному. Несуществующий случайный путь не подходит: он может возвращать 404 в обоих режимах. Повторите проверку для дополнительных назначенных IPv4/IPv6-адресов выбранного интерфейса; IPv6-адрес в HTTP URL заключайте в квадратные скобки.

### 2. Выключение функции

Верните `INTERFACE_MODES=0`, не меняя AP и сеть. После периода применения обе открытые страницы должны автоматически перейти к видео. Проверьте режим в заголовках и реальное продвижение видео; наличие HTTP 200 само по себе не доказывает воспроизведение.

### 3. Отсутствующий интерфейс

В тестовом окружении укажите в `STILL_INTERFACES` имя, отсутствующее в выводе `ip link`. Его отсутствие не должно блокировать HTTP, AP или видео на существующих адресах. В частности, Pi без второго USB-адаптера не должна ждать появления `eth1`, чтобы обслуживать `wlan0`. После проверки восстановите нужный список.

### 4. Изменение адреса

В контролируемой сети смените DHCP-адрес выбранного интерфейса или назначение его адресов. После очередного опроса новый текущий адрес должен получить статичный режим; удалённый адрес больше не должен оставаться в актуальной карте. Проверяйте только реально назначенные и достижимые адреса: отсутствие ответа по удалённому IP не доказывает корректность карты. Убедитесь, что режим видео по другим адресам сохранился.

## Диагностика и границы

На Pi через административный SSH:

```sh
cat /run/player-network/presentation.map
cat /run/player-network/error.log
```

Это root-owned runtime-файлы: карта представления и ошибки применения. `error.log` удаляется после успешной итерации, поэтому его отсутствие нормально. При ошибке конфигурации или проверки nginx сохраняется предыдущая карта; дополнительные журналы — `/run/player-network/nginx-check.log` и `/run/player-network/nginx-reload.log`. Секреты в журналы не записываются; не копируйте содержимое конфигурации с паролем AP в отчёт. При проблеме сохраните дату, версию образа, фактические имена/адреса интерфейсов, наблюдаемый режим и соответствующую ошибку.

Функция не создаёт второй Ethernet-порт, не задаёт адреса/DHCP и не заменяет сетевую маршрутизацию. Производительность и изоляцию разных клиентов нужно оценивать отдельно. Для существующих длительных соединений допустим переходный период; это не механизм контроля доступа.

### QEMU с двумя интерфейсами

Команды ниже соответствуют обновлённому launcher. Выполняйте их с **образом с новой функцией**, хеш которого указан выше; прежний рабочий baseline её не содержит. Нужны `qemu-system-aarch64`, `qemu-img`, Python и клиентские SSH/SFTP; установите их стандартным для вашей системы способом, как указано в [README](../README.md). Наличие частной копии QEMU в служебном каталоге само по себе не добавляет `qemu-img` в PATH.

`--dual-network` поддерживается только для ARM `virt` (режим по умолчанию), не для `--raspi4`. Из корня проекта, при остановленной прежней VM с этим QMP и overlay:

```bash
PIPLAYER_SSH_PORT=2224 \
PIPLAYER_HTTP_PORT=8082 \
PIPLAYER_SECOND_SSH_PORT=2225 \
PIPLAYER_SECOND_HTTP_PORT=8083 \
PIPLAYER_QMP_SOCKET="$PWD/.build/qemu-ethernet.qmp" \
scripts/run-qemu.sh --dual-network --reset
```

Reset удаляет только тестовое состояние выбранного overlay; не запускайте его для работающей VM. Для dual используется отдельный `.build/qemu-virt-dual.qcow2` и соответствующий файл базового SHA256. Пробросы слушают только localhost:

| Сеть | Адрес внутри гостя | SSH/SFTP хоста | HTTP хоста |
| --- | --- | --- | --- |
| net0 | `10.0.2.15` | `127.0.0.1:2224` | `127.0.0.1:8082` |
| net1 | `10.0.3.15` | `127.0.0.1:2225` | `127.0.0.1:8083` |

Имена интерфейсов не следуют номеру netdev: в диагностическом запуске `eth1` получил `10.0.2.15`, а `eth0` — `10.0.3.15`. При настройке вручную сначала проверьте `ip addr`. Сам по себе порт 8082 не означает статичный режим: он станет статичным, только когда интерфейс с адресом `10.0.2.15` выбран в `STILL_INTERFACES`.

Пока VM работает, во втором терминале из корня проекта:

```bash
python3 scripts/smoke-interface-modes.py --reboot
```

Скрипт использует SSH `:2225`, проверяет обе гостевые сети и сам находит имя интерфейса net0. Требуются исходная конфигурация `INTERFACE_MODES=0` и `.build/demo.mp4` с аудио. Ключ по умолчанию берётся из локальной конфигурации проекта; для другого комплекта его путь задаётся `--key`. Не выводите ключи или конфигурацию с паролем AP в отчёт.

Проверка **изменяет тестовую VM**: заменяет активное видео, временно включает статичный режим net0 (HTTP `:8082`), проверяет видео net1 (`:8083`), JPEG/SFTP, Host, HLS, переключение off, адресные alias и по флагу reboot. В `finally` она восстанавливает исходную конфигурацию и прежнюю пользовательскую картинку и ожидает видео на обоих адресах. Активный видеоролик после теста остаётся тестовым. При аварийном завершении самого скрипта, потере связи или питания восстановление не гарантируется: проверьте конфигурацию перед следующим прогоном.

Приведённый выше финальный прогон получил STILL SMOKE PASS, включая HTTP по IPv6 без SKIP. В других окружениях проверка IPv6 карты не равна HTTP-проверке IPv6: smoke может явно вывести SKIP, если гостевой wget не поддерживает такой URL; учитывайте его отдельно. Автоматический smoke оценивает ответы HTTP, поэтому переход открытых страниц проверяется браузером дополнительно; для текущей VM такой визуальный прогон также выполнен. Физический тест нового raw и двух NIC остаётся открытым: второго USB Ethernet-адаптера сейчас нет. Не переносите имена `eth1`/`eth0` из QEMU на номера физических портов Pi.
