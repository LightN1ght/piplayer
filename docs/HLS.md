# Просмотр HLS во внешней программе

Для браузера откройте [страницу PiPlayer](http://192.168.50.1:8080/).

Для программы с поддержкой HLS откройте **[http://192.168.50.1:8080/stream.m3u8](http://192.168.50.1:8080/stream.m3u8)** как сетевой поток. JavaScript и открытие веб-страницы для этого не нужны. Через Ethernet используйте DHCP-адрес Pi с тем же портом 8080 и путём `/stream.m3u8`.

`stream.m3u8` — фиксированный адрес общего живого потока. При замене ролика адрес для программы остаётся прежним. Выражение «без плейлиста» здесь означает отсутствие пользовательской очереди роликов: служебный HLS-плейлист `.m3u8` необходим для передачи сегментов. На устройстве один активный файл, который проигрывается по кругу.

**Статус:** версия собрана из исходников и проверена в чистой ARM VM. Ранее проверенный raw SHA256 `a111a19f1347ed81cf75625a5b08aae4ef1b4f7d01e9cb9833362152505e00cb`, размер 470 810 624 байта. Хостовые 17 тестов PASS за 54,225 секунды (`.build/hls-host-tests.log`). Физическая приёмка публичного образа с индивидуальной настройкой пока не проведена. Точная программа организатора неизвестна, совместимость со всеми клиентами не заявляется. Полный протокол: [VALIDATION](../agents/VALIDATION.md), оперативное состояние: [CURRENT_STATE](../agents/CURRENT_STATE.md).

Целевые проверки нового raw:

- `.build/smoke-interface-hls-final.log`: STILL SMOKE PASS с reboot, IPv4/IPv6 и ответами fixed m3u8 404/200 по выбранному адресу.
- `.build/smoke-hls-regression-final.log`: базовый SMOKE PASS с reboot.
- `.build/smoke-direct-hls-final.log`: DIRECT HLS SMOKE PASS — один FFmpeg-клиент получил смену красного ролика синим, AAC и сохранённые URI. Сравнение кадров нормализует разрешение; это не транскодирование потока на Pi.
- `.build/mpv-hls-final.log`: mpv завершился с кодом 0 после примерно 8 секунд H.264/AAC. Запуск с `--vo=null --ao=null` проверяет декодирование, **не слышимость**. Пример для второй сети тестовой VM: `mpv --no-config --vo=null --ao=null --length=8 http://127.0.0.1:8083/stream.m3u8`.

Первый direct-прогон завершился timeout; его журнал сохранён. Последующий тест нормализует разрешение кадров, но первоначальная причина не установлена из-за утраченного временного stderr. Этот эпизод не является доказанной ошибкой или исправлением runtime.

## Загрузка и подготовка

Видео публикуется по прежнему SFTP-контракту от пользователя `player`:

1. Загрузите MP4 в `/data/incoming/video.part`.
2. Дождитесь завершения передачи.
3. Переименуйте файл в `/data/incoming/video.ready.mp4`.

После проверки новый файл заменит `/data/media/current.mp4`. Незавершённый `.part` не проигрывается. Не загружайте прямо в активный файл и не создавайте очередь: каталог incoming служит для публикации замены, а не расписания роликов. Подробности SFTP: [QUICKSTART](QUICKSTART.md).

Формат: **MP4, H.264 8 bit yuv420p, AAC**; видео без аудиодорожки также допускается. Если файл проходит проверки, Pi передаёт его потоки без перекодирования. На Pi транскодирования нет.

Для ограниченного RAM-буфера проверяются не только кодеки:

- Разрывы между ключевыми кадрами, включая границу зацикливания, должны укладываться примерно в 4 секунды.
- Суммарный объём пакетов выбранных видео- и аудиопотоков ограничен 6 Мбит/с: не больше 750 000 байт в каждой односекундной корзине временных меток и в среднем за длительность пакетов. Это анализ реальных пакетов, не поле среднего битрейта контейнера и не точная оценка HTTP/TS-трафика.

При превышении этих ограничений файл получает суффикс `.rejected`, а `status.json` — ошибку `needs_preparation`. Прежний ролик продолжает играть. Подготовьте видео **на компьютере** и загрузите результат заново:

```bash
scripts/prepare-video.sh input.mov output.mp4
```

Нужен хостовый FFmpeg с libx264. Скрипт задаёт H.264/yuv420p, до 1280 пикселей по ширине, 25 fps, GOP 2 секунды, целевой видеобитрейт 2 Мбит/с, maxrate 3 Мбит/с, bufsize 2 Мбит и AAC 128 кбит/с. Выходной файл не перезаписывается автоматически.

Если в файловой системе HLS-буфера свободно меньше **40 MiB**, завершённый `.ready.mp4` остаётся ожидать освобождения места (`error=buffer_busy`), прежнее видео продолжает играть. Это проверка свободного места tmpfs `/run/player`, не измерение общего MemAvailable системы. **Повторная загрузка не нужна**: не создавайте дополнительные копии, дождитесь обработки существующего ready-файла. При частых заменах место освобождается после удержания старых сегментов.

## Постоянный URL и смена ролика

Браузер продолжает использовать внутренний путь `/hls/<generation>/index.m3u8` и сам переподключается при смене поколения. Для внешней программы используйте `/stream.m3u8`: приватное имя поколения вручную копировать не требуется.

Публикация общего плейлиста выполняется в RAM процессом `/usr/bin/player-publish` и `/usr/libexec/player-publish.awk`. Это shell/awk-реализация без добавления Python или библиотек на Pi. `playerd` запускает дочерний publisher и следит за его heartbeat. Плейлист публикуется атомарно после проверки наличия файлов сегментов.

Поток использует общую `EXT-X-MEDIA-SEQUENCE`, метки `EXT-X-DISCONTINUITY` и `EXT-X-DISCONTINUITY-SEQUENCE`, чтобы внешний клиент мог продолжать чтение после замены ролика или изменения внутреннего поколения. TARGETDURATION составляет 6 секунд; после наполнения публикуемое окно составляет примерно 20–26 секунд. Сегменты, вышедшие из окна, сохраняются ещё как минимум 36 секунд для запаздывающих запросов. На старте окно короче, пока накопятся сегменты.

Сегменты, состояние publisher и логи находятся в tmpfs `/run/player` размером 96 MiB; они не увеличивают размер raw и не требуют постоянной записи HLS на носитель. Требование к raw для бюджета карты 512 MB сохраняется; это не новая аппаратная проверка физической карты такого размера.

Смена картинки во внешнем клиенте видна после его буферной задержки. Точная синхронизация клиентов и переход с нулевыми пропусками на границе роликов не гарантируются: обработка discontinuity зависит также от клиентской программы.

При рестарте publisher в пределах одной загрузки его RAM-состояние сохраняется. После перезагрузки самой Pi глобальные номера и RAM-состояние сбрасываются. Если внешняя программа сама не переподключилась, откройте **тот же URL** заново; менять адрес потока не требуется.

## Совместимость со статичным режимом

При `INTERFACE_MODES=0` по умолчанию видео доступно на всех адресах. Когда включён статичный режим для адреса интерфейса, **`/stream.m3u8` и `/hls/…` по этому адресу возвращают HTTP 404**. Это ожидаемое поведение; используйте адрес видеоинтерфейса. Решение принимается по адресу назначения, не по IP клиента или заголовку Host. См. [ETHERNET](ETHERNET.md).

## Проверка и диагностика

Для быстрой проверки с компьютера, когда опубликовано видео:

```bash
curl -i http://192.168.50.1:8080/stream.m3u8
```

На видеоадресе ожидаются HTTP 200, HLS MIME type и строки `#EXTM3U`, `#EXT-X-MEDIA-SEQUENCE`, `#EXTINF`. По мере работы номера и список сегментов меняются. Один HTTP 200 ещё не доказывает декодирование и звук; окончательная проверка — воспроизведение в требуемой внешней программе, цикл и смена ролика при неизменном URL.

Через административный SSH на Pi можно прочитать:

```sh
cat /run/player/status.json
cat /run/player/stream-error.log
cat /run/player/publisher.log
```

`stream-error.log` может отсутствовать после успешной публикации. Для проверки ресурса используйте `df -h /run/player`; не выводите конфигурацию AP с паролем. При ошибке запишите версию образа, программу-клиент, код HTTP, состояние/ошибку сервиса и момент замены ролика.

Подтверждённый хостовый тест `tests/test_direct_hls.py` завершился за 14,516 секунды: один FFmpeg-клиент с неизменным PID читал HTTP URL до и после SFTP-контракта замены красного ролика синим; изменился framemd5, декодирован ненулевой AAC, старые опубликованные URI сохранялись. Ролики с GOP 8 секунд и CBR 20 Мбит/с отклонены как `needs_preparation` без остановки прежнего видео. Этот хостовый результат дополняется целевыми проверками выше, но не заменяет проверку конкретной программы организатора.
