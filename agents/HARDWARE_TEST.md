# Приёмка на Raspberry Pi 4 B

Аппаратная проверка возобновлена. Картридера нет; пользователь нашёл отдельную ненужную USB-флешку 32 GB и явно разрешил её перезаписать. Основную microSD со старым Debian пока сохраняем как запасной способ загрузки. Питание USB-C и Ethernet к домашнему роутеру доступны.

## Проверка с USB без картридера

1. На ноутбуке определить именно выбранную пользователем флешку по USB-модели, ёмкости и идентификатору. Отмонтировать разделы, записать весь raw-образ и проверить SHA256 обратным чтением первых 470810624 байт. Сохранить журнал в `.build/usb-flash.log`; успешная запись не означает успешную загрузку Pi.
2. После успешной проверки безопасно отключить носитель. Обесточить Pi, извлечь старую microSD и сохранить её отдельно. Вставить записанную флешку в синий USB-порт Pi, подключить Ethernet к роутеру и подать питание.
3. Ждать до 90 секунд; искать `piplayer` в DHCP роутера, доступность SSH/HTTP и SSID PiPlayer. Не принимать старый Debian с SSH/Immich/Home Assistant за новую систему.
4. USB boot зависит от EEPROM и `BOOT_ORDER` платы: [официальная документация](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#usb-mass-storage-boot). Наличие Pi 4 само по себе не подтверждает текущую настройку. При отсутствии загрузки не менять EEPROM вслепую; записать наблюдения, затем вернуть старую microSD при отключённом питании.

В образе root указан через PARTUUID, драйверы USB mass storage/xHCI/SCSI включены в kernel. USB-флешка используется только как путь аппаратной проверки: размер финального raw остаётся 449 MiB и проверка лимита 512 MB сохраняется. Разделы автоматически не расширяются до 32 GB.

## Подготовка

- Использовать финальный `dist/piplayer-rpi4.img` либо `.img.xz`, чей SHA256 совпадает с итоговым VALIDATION. Диагностический `.build/candidate-rpi4.img` для передачи не подходит.
- Питание Pi 4 через USB-C, желательно штатный/качественный источник. На первой проверке оставить лишние USB-устройства отключёнными.
- Вставить карту в ноутбук/ридер и сверить модель/ёмкость носителя. Образ записывается на весь носитель; нужный диск должен быть определён до записи.
- В Raspberry Pi Imager выбрать свой образ (Use Custom), нужную microSD и выполнить запись с проверкой. Пользовательские настройки Raspberry Pi OS в Imager не применяются: учётные данные уже подготовлены нашей сборкой.

## Первое включение через Ethernet

1. Подключить Ethernet к домашнему роутеру, вставить записанную карту, подать питание.
2. Дать первому запуску до минуты: генерируется SSH host key и запускаются сервисы.
3. В DHCP-клиентах роутера найти hostname `piplayer`, записать выданный IP. `.local`-имя не обещается: Avahi/mDNS в образе нет.
4. Открыть `http://IP:8080`: должен быть чёрный экран с приглашением загрузить видео.
5. Проверить SFTP `player@IP:22` паролем из приватного credentials.json. Загрузить demo.mp4 в `/data/incoming/test.part`, затем переименовать в `test.ready.mp4`.
6. Дождаться видео, нажать «Смотреть со звуком», прослушать несколько циклов. Звук воспроизводится на устройстве с браузером; аудиовыход самой Pi для этого не нужен.

## Точка доступа

1. Проверить появление SSID из credentials.json, подключиться соответствующим паролем. Сообщение «без Интернета» ожидаемо.
2. Клиент должен получить 192.168.50.20–100; адрес Pi по умолчанию 192.168.50.1.
3. Открыть `http://192.168.50.1:8080`, проверить видео и звук.
4. Если есть второе устройство, удобно проверять AP с него, сохранив ноутбук в домашней сети для диагностического SSH через Ethernet. Если устройство одно — при сбое AP вернуться в домашнюю сеть и читать логи по Ethernet.

## Функциональные проверки

| Проверка | Ожидаемый результат |
|---|---|
| Видео дольше длительности файла | Продолжается общий HLS, новые сегменты, несколько циклов без остановки |
| Слышимый звук | Слышен тестовый тон или звук собственного ролика после нажатия |
| Fullscreen | В обычном браузере кнопка переводит видео в настоящий fullscreen; выход Esc |
| Новая корректная загрузка | Текущий ролик играет до завершения передачи, затем новый активируется |
| Неподходящий файл | `.rejected`, прежний поток продолжается |
| Reboot по административному SSH | Сохранились ролик и host key; AP и видео поднялись сами |
| Ethernet без кабеля при загрузке | Загрузка/AP не заблокированы; кабель, подключённый позднее, получает DHCP |
| Два клиента | Видят один live-поток; звук/запуск браузера управляются каждым клиентом отдельно |
| 15–30 минут работы | Нет роста количества сегментов/логов без ограничения, неожиданных перезапусков или ошибок SD |

## Диагностика без вывода секретов

Административный SSH: `ssh -i dist/admin_ed25519 root@IP`. Не публиковать ключ, пароль, `/etc/player/player.conf` или содержимое конфигов hostapd.

```sh
cat /run/player/status.json
cat /run/player/ffmpeg.log
cat /run/player/ap.log
ip address
df -h /data /run/player
dmesg | tail -60
```

Записывать результат в VALIDATION с хешем образа, моделью/объёмом RAM платы, способом подключения, браузером и фактическими PASS/FAIL. При сбое не менять несколько подсистем сразу: сначала сохранить диагностику, затем исправить owning source и собрать новый образ.
