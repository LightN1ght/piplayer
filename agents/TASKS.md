# PiPlayer: рабочие задачи

Обновлено 6 ноября 2026. Начинать продолжение с [CURRENT_STATE.md](CURRENT_STATE.md). Дедлайн: **6 ноября 2026, 16:00 МСК**. «Выполнено» ниже относится только к указанной среде и версии. При обновлении образа результаты привязывать к его SHA256, дате и среде в [VALIDATION.md](VALIDATION.md).

Владельцы: **Sol** — документирование; **Terra** — независимый review и тесты; **Luna** — первичная сборка; **root** — интеграция, актуализация сборки и QEMU; **плата** — пользователь у физической Pi при поддержке root. Общий статус и окончательную поставку ведёт root.

## T1. Зафиксировать сценарий и границы

- Владелец: Sol / root.
- Вход: требования пользователя и текущие исходники.
- Выход: `PROJECT.md`, `ARCHITECTURE.md`, `ROADMAP.md`, этот список задач; связанная инструкция QUICKSTART.
- Зависимости: нет.
- Проверка: Pi 4 B, AP при старте, SSH/SFTP, общий цикл HLS со звуком, чёрный фон, все адреса :8080, raw для 512 MB; Ethernet №1/№2 не обязателен для базовой версии; пользователь отдельно запросил расширение E1–E4. Статусы не смешивают хост, QEMU и плату.
- Статус: выполнено. Четыре документа подготовлены и синхронизированы с финальной сборкой; оперативные изменения вносить после новых прогонов.

## T2. Сохранить и восстановить сборку

- Владелец: Luna — первичная сборка; root — интеграция и актуализация.
- Вход: исходники, `.build/downloads`, хостовые зависимости; утраченная после выключения сборка в `/tmp` не считается доступной.
- Выход: постоянный `PIPLAYER_WORK` без пробелов, успешно восстановленная Buildroot 2025.02.19 сборка, журнал `.build/build.log`.
- Зависимости: нет; документация и хостовые проверки не блокируют запуск.
- Проверка: сборка без root, наличие ожидаемых kernel/DTB/rootfs/images, отсутствие секретов в отчёте. Не менять toolchain поверх несовместимого output.
- Статус: выполнено. Полная сборка и свежий повторный `--configure` успешно завершены в `/home/light/.cache/piplayer-build`; актуальные исходники синхронизированы. По умолчанию build.sh выбирает `${XDG_CACHE_HOME:-$HOME/.cache}/piplayer-build`.

## T3. Включить исправления boot и сети в новый raw

- Владелец: Luna — первичная сборка; root — интеграция и актуализация.
- Вход: T2; `genimage.cfg`, `cmdline.txt`, `S40network`, `run-qemu.sh` с внесёнными исправлениями.
- Выход: обновлённые raw, `dist/boot`, `.xz`, SHA256SUMS из одной сборки.
- Зависимости: T2.
- Проверка: `scripts/check-image.py`, raw ≤ 480 000 000 байт; MBR signature `0x504c4159` и root `PARTUUID=504c4159-02` согласованы; boot/rootfs не взяты от разных сборок; DHCP ищет `eth*`, `en*`, `usb*`; в rootfs есть `stat -c` (BusyBox STAT и FEATURE_STAT_FORMAT из нового fragment), новый watchdog и проверка обязательных команд.
- Статус: выполнено. Финальный raw 470 810 624 байта, SHA256 `8f4d68e889ba43e24a93ca73bdbd167ea482a1bc237b70ba23cbcc83a27903fc`; `.xz` около 28 MiB, SHA256 `3e3e7442f03ac7eee153cb31e78c2d18f6ffe71d60cd1f8f63ac69b4d4392a61`. BusyBox STAT/FEATURE_STAT_FORMAT и `/bin/stat` присутствуют.
- Стоп: превышение размера или неверная структура запрещают переход к передаче.

## T4. Пройти чистую загрузку и smoke в QEMU

- Владелец: root; независимая проверка — Terra.
- Вход: согласованные raw и boot из T3, QEMU ARM `virt` по умолчанию, `qemu-img`, тестовый AAC-ролик; для `--raspi4` также `fdtput/fdtget`.
- Выход: boot-лог и отчёт с SHA256 образа, доступными SSH :2222 и HTTP :8080 на localhost, результат `smoke.py --reboot`.
- Зависимости: T3. Перед сменой raw остановить старый QEMU; затем `scripts/run-qemu.sh --reset` удалит тестовые данные overlay. Скрипт проверяет сохранённый raw SHA256, запрещает reset работающей VM и для `--raspi4` создаёт частный DT с UART aliases и отключённым дочерним Bluetooth заново.
- Проверка: root найден через PARTUUID; virtio-net/blk работают; для raspi4b дополнительно проверить UART после alias fix и сеть `usb0`; SFTP от `player`, HLS/AAC с декодированием непустого звука, отклонение плохого файла, восстановление после SIGKILL и отсутствия продвижения/SIGSTOP, reboot и сохранение ролика.
- Статус: ARM virt PASS на финальном raw из чистого overlay без ручных дополнений: `.build/smoke-final.log`, SMOKE PASS с SFTP, продвижением HLS, ненулевым AAC, восстановлением FFmpeg и reboot. Отдельная проверка финального raw на raspi4b завершилась SMOKE PASS; холодный запуск с ожиданием SSH также PASS, тестовая VM остановлена. Основная virt VM остаётся на :2222/:8080. Нативный 60-секундный watchdog также ранее проверен в диагностической ARM VM; это отдельный результат.
- Ограничение: USB-сеть raspi4b измерена в 0,864–0,889 Мбит/с при demo около 1,1 Мбит/с, поэтому для просмотра по умолчанию выбран ARM virt (103–130 Мбит/с). Это тот же raw и Pi Image, а не аппаратная оценка скорости. Overlay теперь `.build/qemu-$machine.qcow2`.
- Стоп: зависание загрузки или недоступность обязательных сервисов требует boot/сетевой диагностики; Wi-Fi по QEMU не принимается.

## T5. Подтвердить медиасервис на хосте

- Владелец: Terra — независимый review и тесты; root — интеграция исправлений.
- Вход: `playerd`, `tests/test_media.py`, host FFmpeg/ffprobe с libx264.
- Выход: результат `python3 -m unittest discover -s tests -v` и при изменениях повторная проверка затронутого поведения.
- Зависимости: нет; можно выполнять независимо от сборки.
- Проверка: реальный HLS H.264/AAC, цикл дольше входного ролика, игнорирование `.part`, отклонение испорченного файла без остановки текущего, замена поколения, восстановление после SIGKILL и SIGSTOP, реальное продвижение плейлиста вместо одной проверки его наличия.
- Статус: выполнено на x86_64, обновлённый интеграционный сценарий прошёл (последний записанный прогон — 31,37 секунды); покрывает продвижение HLS, SIGKILL и SIGSTOP. Watchdog по умолчанию срабатывает после 60 секунд без продвижения; перед TERM отправляет CONT. Этот результат не подтверждает ARM-сервисы или сеть устройства.

## T6. Проверить браузер, слышимый звук и fullscreen

- Владелец: root; пользователь для обычного браузера и прослушивания.
- Вход: HTTP-плеер с настоящим HLS, короткий ролик со слышимым AAC; после T4 или T7 повторить с целевого устройства.
- Выход: браузер/устройство/версия образа, результат нескольких циклов, кнопки звука, чёрного фона и нативного fullscreen.
- Зависимости: для хостового UI — T5; для целевого образа — T4 либо T7.
- Проверка: растёт currentTime за длительностью исходника, нет остановки на конце, звук действительно слышен после кнопки, пропорции сохранены, fullscreen включается в поддерживающем обычном браузере; два клиента получают одно поколение потока.
- Статус: плавное воспроизведение со слышимым звуком подтверждено пользователем в Helium после Ctrl+Shift+R и 30–60 секунд просмотра финальной ARM virt VM: «Да, теперь плавно со звуком». Позже пользователь подтвердил на реальной Pi плавное видео, слышимый звук и нативный fullscreen, а также просмотр с телефона через AP. 6ноября пользователь подтвердил60с одновременного просмотра ноутбук+телефон со звуком без остановок. IAB ранее подтвердил HLS и `muted=false`, но его старые фоновые DOM-снимки не доказывают остановки backend. UI использует hls.js первым при MSE, native HLS как fallback и повторный play по кнопке.

## T7. Аппаратная приёмка Pi 4 B

- Владелец: пользователь у платы / root.
- Вход: проверенный по структуре raw из T3, Pi 4 B, питание, microSD фактической ёмкости не меньше raw, клиент с Wi-Fi и браузером, тестовый AAC-ролик. Запись стирает карту: выбранный носитель проверяет пользователь.
- Выход: аппаратный протокол с SHA256 raw, моделью платы, клиентом, сетевыми адресами и результатами.
- Зависимости: T3; T4 желателен для предварительного исключения ошибок сервисов, но не заменяет этот этап.
- Проверка: холодный старт → AP без ручных команд → DHCP → SSH/SFTP → загрузка `.part`/rename → HTTP :8080 → несколько циклов со звуком; затем плохая/незавершённая загрузка, замена ролика, Ethernet DHCP/HTTP, reboot и сохранение ролика. Проверить T6 в обычном браузере. Записать длительность фактического непрерывного прогона и свободное место `/data`.
- Статус: USB FLASH PASS и реальный firmware boot подтверждены. Pi4B Rev1.2 успешно загрузилась с USB, Ethernet192.168.0.126; аппаратный smoke с SSH/SFTP, HLS/AAC, reject, recovery и reboot: **SMOKE PASS** (`.build/smoke-hardware.log`). Пользователь подтвердил браузер со звуком/fullscreen и просмотр с телефона через AP; на Pi есть DHCP-аренда. 6ноября пользователь подтвердил SFTP через Wi-Fi с Android и замену на собственный ролик со звуком. Монитор ноутбука прервался из-за ENETUNREACH, поток Pi остался прежним. Независимый монитор на Pi завершён: HARDWARE LOCAL SOAK PASS,901с/180проверок без перезапуска потока; сохранён `.build/hardware-soak-local.log`. Пользователь подтвердил холодный старт без Ethernet; после подключения кабеля на88-й секунде DHCP/SSH/поток и сохранённый ролик подтверждены, `.build/hardware-coldboot.log`. Основной сценарий принят. Старую microSD и EEPROM не меняли. Чек-лист: [HARDWARE_TEST.md](HARDWARE_TEST.md).
- Стоп: неработающий AP, SFTP, звук, цикл или восстановление после reboot блокируют аппаратную приёмку. Недоступность платы фиксируется как отсутствие проверки, а не PASS.

## Интеграция и правила остановки

- **F1. Реальный ролик и SFTP через Wi-Fi.** Пользователь сейчас вне дома с Pi, без Ethernet. Ноутбук остаётся в своей сети с Интернетом: переключать его Wi-Fi не требуется. На Android пользователь устанавливает Material Files, подключается к PiPlayer и загружает копию собственного H.264/AAC-ролика как `/data/incoming/phone-test.part`; после конца передачи переименовывает в `phone-test.ready.mp4`, проверяет смену видео и слышимый звук. Статус: подтверждено пользователем — «Да, мой ролик играет со звуком» после SFTP/rename через Wi-Fi. Личный ролик не включать в Git или архив исходников.
- **F2. Два реальных клиента.** Одновременный просмотр с двух устройств, минимум60с. Синхронность кадр в кадр не требуется; оба должны получать одно активное видео без остановок. Статус: подтверждено пользователем — ноутбук+телефон60с одновременно, оба со звуком без остановок. Pixel6/Chrome ранее не открыл HTTP, причина не установлена и устройство стало недоступно; этот отдельный случай не считается исправленным. Ноутбук пользователь переключал сам и вернул Интернет; инструменты сеть не меняли.
- **F3. Приватный GitHub — выполнено.** https://github.com/LightN1ght/piplayer, private, ветка main. Первый коммит `74adf74a70d9e963220083b5dda998be9c3077eb` отправлен и сверён через API; приватность проверена. README, документация, скрипты и тесты опубликованы. Перед commit проверены49файлов Git-индекса: секретов/образов/личного ролика нет. Последующие правки статуса документов отправляются обычным новым коммитом. Лицензия проекта отдельно не выбрана.

Последовательность критического пути: **T2 → T3 → T4/T7 → T8**. T5 и хостовая часть T6 независимы от восстановления сборки. T7 требует участия пользователя у платы и возобновлена через подготовку USB-носителя; выполнять по HARDWARE_TEST, не предполагать аппаратную проверку выполненной.

Изменения boot/разметки интегрируются через новую сборку T3; изменения медиасервиса — через T5, затем проверку на обновлённом устройстве. Контракт `.part → .ready.mp4`, `status.json`, HTTP-пути и имена артефактов должны оставаться согласованными между upload, playerd, UI, smoke и QUICKSTART.

При нехватке времени остановить расширение объёма. Неподтверждённый образ передавать только со статусом предварительной сборки и конкретными блокерами. Не заменять аппаратные результаты хостовыми тестами и не снижать предел размера ради формального завершения задачи.

- **E3, сборка — выполнено, чистая VM принята.** Новый raw из исходников: 470810624 байта, SHA256 `a111a19f1347ed81cf75625a5b08aae4ef1b4f7d01e9cb9833362152505e00cb`. Старый baseline сохранён отдельно. Физический второй Ethernet не проверен: адаптера нет.

## H1–H3. Прямой HLS для внешней программы

- **H1, реализация и хост — выполнено.** Постоянный `/stream.m3u8`, общая нумерация сегментов и discontinuity при замене файла, ограниченное хранение сегментов в RAM, watchdog publisher. Все 17 хостовых тестов PASS за 54.225с, `.build/hls-host-tests.log`.
- **H2, окончательный ARM raw — выполнено в VM.** Обычный, двухсетевой и прямой HLS smoke PASS; один FFmpeg-клиент пережил SFTP-замену red→blue, AAC декодирован. mpv8с PASS; отсрочка при заполненном tmpfs и последующая активация без повторной загрузки PASS. Логи в VALIDATION. Аппаратная проверка новых функций ещё не выполнена.
- **H3, документация/Git — выполнено.** Постоянный URL, профиль GOP/битрейта и подготовка ролика, результаты и ограничения описаны; [PR #1](https://github.com/LightN1ght/piplayer/pull/1). Программа организатора неизвестна, совместимость с ней ещё не подтверждена.

Следующий этап после программных проверок — обновление физической Pi и аппаратная проверка новых функций. Сеть ноутбука автоматически не переключать. Обновление флешки выполнять только после повторной идентификации выбранного носителя.
