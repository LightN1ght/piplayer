# PiPlayer

Автономный сетевой видеоплеер для Raspberry Pi 4 Model B. После включения Pi поднимает Wi-Fi-точку доступа, принимает видео по SFTP и непрерывно транслирует его по кругу в браузер со звуком. Интернет для просмотра не нужен. Для внешней HLS-программы предусмотрен постоянный URL `/stream.m3u8` без JavaScript; точная программа организатора пока неизвестна.

Страница работает на порту **8080**: чёрный фон, видео с сохранением пропорций, кнопка включения звука и fullscreen. Сервер слушает все IPv4/IPv6-адреса устройства; через Ethernet используется адрес, полученный по DHCP. Все зрители получают общий HLS-поток, с возможной разницей в задержке браузеров.

```text
Компьютер → подготовка MP4 → SFTP (.part → .ready.mp4)
                                      ↓
                         Pi: проверка → активное видео
                                      ↓
                         FFmpeg: бесконечный цикл → HLS в RAM
                                      ↓
                         nginx :8080 → браузер по Wi-Fi / Ethernet
```

Система собрана на Buildroot 2025.02.19: Linux Raspberry Pi 6.6, BusyBox init, OpenSSH, nginx, FFmpeg, hostapd и dnsmasq. Графической оболочки и компилятора в целевом образе нет.

## Состояние проверки

Новая версия с постоянным `/stream.m3u8` собрана и проверена в чистой ARM VM: базовый и двухсетевой smoke с reboot, внешний FFmpeg-клиент со сменой ролика и mpv с H.264/AAC. Хостовые 17 тестов PASS за 54,225 секунды. Точная программа организатора неизвестна; mpv с null-выводом не проверяет слышимость звука.

На физической Pi пока проверен прежний базовый образ: новые HLS/Ethernet-функции требуют обновления устройства и отдельной аппаратной проверки. История и точные границы: [VALIDATION](docs/VALIDATION.md).

## Образ и хранение

Текущий raw-образ занимает **470 810 624 байта (449 MiB)**; `.xz` — около 28 MiB. Сборка проверяет предел **480 000 000 байт** для бюджета носителя номиналом 512 MB. SHA256 текущего raw: `a111a19f1347ed81cf75625a5b08aae4ef1b4f7d01e9cb9833362152505e00cb`. Физическая microSD 512 MB отдельно не испытывалась: аппаратные проверки выполнены с USB-флешкой 32 GB.

Разметка фиксированная: MBR, отступ 1 MiB, FAT32 boot 64 MiB и ext4 root/data 384 MiB. Раздел не расширяется автоматически на большой носитель. После тестового ролика свободно около 248 MiB; для замены нужно временное место под старый и новый файлы одновременно. HLS-сегменты и рабочие логи находятся в tmpfs 96 MiB и не пишутся постоянно на носитель.

## Быстрый старт с локальным образом

Нужны Pi 4 B, питание, подходящий носитель, браузер и SFTP-клиент. Если комплекта образа ещё нет, соберите его по инструкции ниже. Готовые образы и данные доступа передаются отдельно: в Git входят исходники и документация.

1. Проверьте локальные файлы комплекта:

   ```bash
   (cd dist && sha256sum -c SHA256SUMS)
   ```

2. Запишите `dist/piplayer-rpi4.img` **целиком на выбранный носитель** через Raspberry Pi Imager или Etcher. Это стирает его данные. Для `.img.xz` нужна программа с поддержкой xz либо предварительная распаковка. USB-загрузка требует уже настроенной поддержки USB boot в Pi; проект не меняет EEPROM.
3. Включите Pi. Подключитесь к AP по SSID и паролю из приватного `credentials.json`. Сообщение «без Интернета» ожидаемо: оставайтесь в этой сети, отключив автоматическое переключение на другую при необходимости.
4. Откройте [плеер через AP](http://192.168.50.1:8080). При Ethernet-подключении найдите `piplayer` среди DHCP-клиентов роутера и откройте его адрес с портом `8080`.
5. Загрузите видео по SFTP, как описано ниже. Нажмите «Смотреть со звуком»; включение звука и fullscreen зависит от действия пользователя и возможностей браузера.

Приватные `credentials.json` и `admin_ed25519` передаются владельцу устройства отдельно. В публичный репозиторий и публичные архивы они не входят. Подробности комплекта: [DELIVERY](docs/DELIVERY.md), пошаговая инструкция: [QUICKSTART](docs/QUICKSTART.md).

## Просмотр во внешней программе

Браузер: [http://192.168.50.1:8080/](http://192.168.50.1:8080/). Для HLS-программы: [http://192.168.50.1:8080/stream.m3u8](http://192.168.50.1:8080/stream.m3u8). Через Ethernet замените адрес на DHCP-адрес Pi, сохранив порт и путь. Служебный m3u8 необходим протоколу; пользовательской очереди роликов нет, активен один файл. Подробнее: [HLS](docs/HLS.md).

После смены ролика URL остаётся прежним; задержка зависит от буфера клиента. После reboot программа без автоматического переподключения может потребовать повторно открыть тот же URL. Совместимость с неизвестной программой организатора пока не подтверждена.

## Формат и загрузка видео

Первая версия принимает **MP4, H.264 8 bit yuv420p, AAC**; допускается видео без звуковой дорожки. Произвольные кодеки на Pi не транскодируются. Рекомендуемая подготовка выполняется на компьютере с FFmpeg и libx264:

```bash
scripts/prepare-video.sh original.mov ready.mp4
```

Скрипт ограничивает ширину до 1280 пикселей, задаёт 25 fps, H.264 main/yuv420p, около 2 Мбит/с, GOP 2 секунды и AAC 128 кбит/с. Он задаёт maxrate 3 Мбит/с и VBV-буфер 2 Мбит и не перезаписывает существующий выходной файл. В новой версии вход проверяется по пакетам: GOP не более 4 секунд (включая цикл), суммарно видео+аудио не более 6 Мбит/с в каждой секундной корзине и в среднем. Превышение даёт `needs_preparation`; подготовьте файл на хосте. При свободном месте HLS tmpfs меньше 40 MiB готовый файл ждёт (`buffer_busy`): повторно загружать его не нужно.

В любом SFTP-клиенте подключитесь к `192.168.50.1:22` как `player`, с паролем из приватного комплекта. Загрузите файл в `/data/incoming/video.part`, дождитесь конца передачи и **переименуйте в `video.ready.mp4`**. Именно rename публикует завершённую загрузку. Префикс имени может быть любым.

Из исходников тот же протокол выполняет скрипт:

```bash
python3 scripts/upload.py ready.mp4 --host 192.168.50.1 --key dist/admin_ed25519
```

После проверки файл становится `/data/media/current.mp4`; браузеры переподключаются к новому поколению HLS. `.part` никогда не проигрываются. Неподходящий файл остаётся с суффиксом `.rejected`, прежнее видео продолжает работать. Не загружайте напрямую в `current.mp4`. Смена файла и восстановление потока могут сопровождаться короткой буферизацией; точная синхронизация кадров разных клиентов не гарантируется.

## Настройки точки доступа

Настройки AP находятся в отдельном файле **на Pi**: `/etc/player/player.conf`. Административный вход:

```bash
ssh -i dist/admin_ed25519 root@192.168.50.1
```

Через SSH измените `AP_SSID`, `AP_PASSWORD`, `AP_COUNTRY`, `AP_CHANNEL` и при необходимости остальные параметры, сохраняя shell-синтаксис и кавычки. Укажите код страны фактического использования: генератор исходной конфигурации по умолчанию задаёт `RU`. Примените на устройстве:

```sh
/etc/init.d/S45accesspoint restart
```

Текущее Wi-Fi-соединение прервётся; подключитесь заново с новыми данными. Локальный `credentials.json` после ручного изменения автоматически не обновляется. AP создаёт локальную сеть без маршрутизации Интернета. Root-пароль отключён, администрирование выполняется индивидуальным SSH-ключом.

## Дополнительные режимы Ethernet

По умолчанию `INTERFACE_MODES=0`: видео на всех адресах. В `/etc/player/player.conf` можно включить `INTERFACE_MODES=1` и указать `STILL_INTERFACES='eth0'` (или несколько реальных имён). По их адресам показывается JPEG/заглушка, остальные адреса сохраняют видео; `/hls/…` и `/stream.m3u8` на статичном адресе возвращают 404. Выбор идёт по адресу назначения, не по клиенту/Host; это не firewall-изоляция. Настройки подхватываются автоматически.

Пользовательский JPEG: SFTP `/data/still/image.part` → `/data/still/image.jpg`. USB NIC подключайте до питания Pi; позднее подключение кабеля и позднее появление USB-адаптера — разные сценарии. Подробности и двухсетевой QEMU: [ETHERNET](docs/ETHERNET.md).

## Сборка из исходников

Нужен Linux x86_64, доступ к публичным источникам зависимостей и свободное место для Buildroot, toolchain и output. Подготовьте `make`, `gcc`, `g++`, `cpio`, `rsync`, `bc`, `unzip`, `wget`, `curl`, `file`, `patch`, `perl`, `python3`, `tar`, `xz`, `bison`, `flex`, `openssl`, `ssh-keygen` и стандартные утилиты сборки. Для upload/smoke нужны клиентские `ssh` и `sftp` из OpenSSH. Скрипт проверяет часть зависимостей, остальные проверяет Buildroot. Для работы с видео и тестов отдельно нужны FFmpeg/ffprobe с libx264 на хосте.

Из корня исходников:

```bash
scripts/build.sh
```

По умолчанию рабочая директория — `${XDG_CACHE_HOME:-$HOME/.cache}/piplayer-build`, параллелизм — 4. Buildroot не принимает пробелы в рабочих путях; при необходимости задайте собственный постоянный путь:

```bash
PIPLAYER_WORK="$HOME/piplayer-build" JOBS=4 scripts/build.sh
```

Скрипт загружает Buildroot с проверкой SHA256, создаёт индивидуальные данные доступа в `.local/`, получает hls.js 1.6.13 с проверкой хешей, копирует проект в рабочую директорию и запускает сборку. Архивы зависимостей сохраняются в `.build/downloads`, журнал — `.build/build.log`. Root не требуется; системные пакеты скрипт не устанавливает.

Результат: `dist/piplayer-rpi4.img`, `.img.xz`, `SHA256SUMS`, boot-файлы, исходники и инструкции, а также **приватные** данные доступа. При повторной сборке данные доступа сохраняются. После изменения defconfig используйте `scripts/build.sh --configure`; смена toolchain требует чистой рабочей директории. Изменения исходников во время сборки не попадают в уже скопированный staged-проект автоматически: повторите запуск для синхронизации.

Перед упаковкой остановите проектные QEMU VM: `package.sh` защищает raw, который используется как backing image. Обновление только документации и архива исходников: `scripts/package-source.sh`.

## Проверки и QEMU

Хостовый интеграционный тест использует реальные FFmpeg/ffprobe:

```bash
python3 -m unittest discover -s tests -v
```

Для эмулятора нужны `qemu-system-aarch64` и `qemu-img`. По умолчанию запускается ARM `virt` Cortex-A72 с VirtIO, **тем же Pi kernel и тем же raw-образом**:

```bash
scripts/run-qemu.sh
```

Плеер: [localhost:8080](http://127.0.0.1:8080), SSH/SFTP: `127.0.0.1:2222`. Пробросы слушают только localhost. В другом терминале можно выполнить smoke на подготовленном ролике **со звуком**:

```bash
python3 scripts/smoke.py --video ready.mp4 --key dist/admin_ed25519 --reboot
```

Smoke заменяет активное видео тестовым, завершает FFmpeg для проверки восстановления и с `--reboot` перезагружает гостя. Он проверяет SSH/SFTP, HLS после конца ролика, декодирование ненулевого AAC и сохранность данных.

`--raspi4` выбирает модель платы `raspi4b`; дополнительно нужны `fdtput/fdtget` из device-tree-compiler. В испытанной версии QEMU её USB-сеть давала около 0,87 Мбит/с, вызывая буферизацию тестового видео. Для просмотра используйте стандартный VirtIO-режим. Оба режима прошли smoke; эмуляция сама по себе не проверяет физический Wi-Fi, Ethernet и firmware boot.

Для каждой модели хранится отдельный overlay `.build/qemu-<machine>.qcow2`. После смены raw сначала остановите соответствующую VM, затем запустите `scripts/run-qemu.sh --reset` (при необходимости с `--raspi4`). Reset удаляет тестовые данные VM; виртуальная ёмкость overlay 512 MiB не является размером образа для записи.

## Что проверено

На 6 ноября 2026:

- Linux x86_64: сборка, проверки образа, интеграционный медиатест, восстановление FFmpeg после SIGKILL и SIGSTOP.
- Чистые ARM virt и raspi4b VM: smoke с SFTP, HLS/AAC, восстановлением и reboot.
- Raspberry Pi 4 B Rev 1.2, 4 GB RAM, USB boot с флешки 32 GB: Ethernet DHCP, SSH/SFTP, замена видео, HLS/AAC, reboot с сохранением ролика и SSH host key.
- Пользователь подтвердил плавное видео, звук и fullscreen на ноутбуке; подключение телефона к AP и просмотр по Wi-Fi; холодный старт без Ethernet. Позднее подключённый Ethernet поднялся автоматически.
- Автоматический локальный прогон на Pi: 901 секунда, 180 проверок HTTP/HLS, без перезапуска потока. Это отдельная проверка сервиса, а не непрерывное наблюдение браузера все 15 минут.

6 ноября пользователь подтвердил SFTP-загрузку собственного H.264/AAC-ролика с Android через Wi-Fi, публикацию переименованием и воспроизведение нового видео со звуком. Пользователь также подтвердил 60 секунд одновременного просмотра на ноутбуке и телефоне со звуком без остановок. Максимальная нагрузка и поддержка произвольных пользовательских роликов не измерены. Режимы по адресам реализованы отдельно как optional-функция и по умолчанию выключены. Полный протокол: [VALIDATION](docs/VALIDATION.md).
